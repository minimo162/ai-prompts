# PAD編集失敗の保全・復旧

この機能は元の依頼の再実行ではありません。Mainを戻して保存する処理に限定し、Runは呼びません。実行開始の予約がある操作は対象外です。

## 保全する記録

専用フローの所有確認後、編集前にジョブのrun領域へ`pad-backup.json`を保存します。元Main、元所有記録のバイト列とハッシュ、提出コードのハッシュ、PADウィンドウのPID・開始時刻・ハンドル、コントローラーのPID・開始時刻を含みます。元の業務本文やクリップボードを診断として外部送信する機能ではありません。元クリップボードの内容はディスクへ保存しません。

`pad-recovery-state.json`は編集の段階を記録します。削除・貼付け要求は操作前、空Main/貼付け内容の観測は確認後、実行開始予約はRun呼出し前に記録します。`pad-preservation.json`はMain・クリップボードの保全結果です。以前のバックアップを新しい操作で上書きしません。

## 画面での復旧

1. 「保全・復旧」に表示された状態を確認します。Main編集が未完了なら、新しい依頼を止めます。途中ファイルは「未確認」と表示し、存在だけで全件成功へ格上げしません。
2. 元のコントローラーが終了してから「停止・内容を確認して元Mainを復元」を押します。対象は、その依頼の最後のPAD操作に限定します。
3. アプリはバックアップ、同じPADウィンドウ、停止・編集可能状態、現在のMainと所有記録を再確認します。元Mainまたは確認済み提出コード（削除確認後は空Main）以外の内容は上書きしません。
4. 元Mainの全文を戻し、保存後にコピー戻しで一致を検証してから元の所有記録を戻します。どちらかが確認できなければ復元完了にはしません。
5. 復旧しても元の依頼は再実行しません。元の依頼の履歴、成果物、claimは残します。

ウィンドウが別、PADが稼働中、元コントローラーが生存中、利用者の追記、所有記録の変更、不正なバックアップ、実行開始済み、貼付け未確定の場合は拒否します。復元ボタンが無効な未確定操作を、単に新しいIDに変えて再送しないでください。専用フローの確認・修復が必要です。

## クリップボード

元の内容は形式を含めてメモリーへ取り込み、取り込み中の変更も検査します。アプリが最後に書いた内容とWindowsの変更番号が一致する場合だけ戻します。同じ文字列でも、別操作が形式等を変更して変更番号が変わった場合は上書きしません。次の書込み前にも変更を検査します。

貼付け要求が未確定の場合は、待っているPADへ元の私的な内容を誤って貼り付けないため、クリップボードを戻さず警告します。復元失敗・未確認は処理結果と別に表示します。後の正常処理やMain復旧だけで、以前のクリップボード警告を消しません。コントローラー終了後に、保存していない元クリップボードを復元できたとは扱いません。

## CSV中断との区別

CSVはPADを操作しません。ワーカーの強制終了後は、確定済み結果と送信予約を照合します。予約ファイルが確実に存在しない準備段階だけを未送信へ戻し、残りを続行できます。アクセス拒否等を「予約なし」にしません。送信予約がある結果不明の要求は再送しません。

## 検証の範囲

- 方針・ファイル試験では、削除確認後・貼付け後・保存中からの復元、元ownerのBOM/空白を含むバイト保持、利用者編集・別ウィンドウ・稼働中・実行開始済み・不正記録の拒否、Save失敗、クリップボード失敗、同じ文字列での変更番号差、再操作の冪等性を検証します。PADとクリップボード境界はmockです。
- 実Edge/PS5 HTTPでは、保全警告、未確認ファイル、復元操作、復元後にも残るクリップボード警告を検証します。ネイティブ復元境界は置換しています。
- CSVは実ワーカープロセスのPID/開始時刻を照合して強制終了し、20件保持・残り30件の続行と重複送信0を検証します。AIはmockです。
- 実PADでは読取りだけを実施し、Main書換え0・Run0、元の空クリップボードへの復元を確認しました。現在のMainに一致する所有記録を確認できなかったため、実機のMain書換え/復元は実施していません。これをnative Save失敗や復旧の合格に数えません。

専用の所有確認済みフローでのnative Save失敗、遅い貼付け、前面変更、スリープ・認証切れ、社内PC・別利用者の受入は残っています。
